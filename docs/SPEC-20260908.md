## Framework choice

OpenSpec fits this existing small tool because a change folder holds a proposal,
behavior deltas, design decisions, and a lane-sized task, while current specs and
archived changes stay distinct. This maps naturally to incremental promotion.
The framework's [documented layout](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)
supports that separation; its [default artifact schema](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)
supplies the Markdown forms used here.

GitHub Spec Kit is also viable. Its [constitution/specify/plan/tasks workflow](https://github.com/github/spec-kit)
provides stronger up-front planning structure. I studied the supplied local generic
installation's workflow instructions, command files, task template, and integration
metadata. It is agent-neutral and its feature directories need not dictate branch
names. The choice is therefore **not** based on an assumed Codex/Claude or branch
incompatibility. Here a second constitution and installed command/template/script
scaffold would duplicate AGENTS.md and add maintenance without improving these
small, separately promoted changes. OpenSpec's change/archive model is the better
fit for this initiative; neither framework needs to become a runtime dependency.

The scaffold is a [config](../openspec/config.yaml), a [portable workflow guide](../openspec/README.md),
an [existing safety spec](../openspec/specs/lane-safety/spec.md), and four standard
artifacts per product change. No agent-specific command registration, custom schema,
runtime package, root dependency, generated installation manifest, or empty archive
placeholder was added. The optional [mouse brief](tasks/board-mouse.md) is research
outside product changes. The installed OpenSpec 1.6.0 rejects spec-less changes even
though current upstream documents a skip_specs option; keeping this research
separate avoids inventing a product requirement or upgrading the machine.

## Goals and constraints

- One board shows every agent visible through accessible local Herdr servers, with
  its repository, goal/provenance, state, exact-commit gate, report/verdict, and a
  one-key jump to its tab. Unregistered, unnamed, and facilitator sessions count.
- A task plus explicit repository and route becomes an ignored template brief, one
  branch/worktree/child workspace, one agent, and one registry entry.
- Each development root can own shared config/routes and sibling worktrees at
  `<root>/.worktrees/<repo>/lane-<topic>`. Same-named repositories remain isolated;
  git, not lane configuration or a label, determines repository and author identity.
- The CLI remains built-ins-only and agent-agnostic. The optional UI calls CLI
  interfaces. There is no scheduler, job store, lifecycle replay, automatic
  promotion, remote gate, push, or identity setter.
- Existing cwd/clean-tree/conflict/archive/validation/fast-forward safeguards and
  Node 20/git 2.38 compatibility remain acceptance requirements.
- All tracked material is public-safe. The raw local briefs and review transcripts
  were read as inputs and were not copied into the repository.

"Machine-wide" means Herdr-discoverable local sessions; inaccessible servers and
agents outside Herdr cannot be promised. The board must show coverage, unknown
fields, and errors honestly. Production root defaults never choose temporary
worktrees; system-temp repositories remain mandatory test fixtures. Legacy paths
and the existing explicit environment override remain usable without migration.

keyboard UX. Message previews can start after the read-interface lane (2b-i).
