## Findings
- [Moderate] lane.mjs:1578 - The completion probe in waitForPrivateReview now strips only newline runs, so a finished record whose final line holds a space or a tab, or which uses CRLF endings, is never recognised as complete; lane review then burns the whole deadline and reports a timeout saying the reviewer may still write late evidence, although the complete record is already on disk. With a four-second deadline the three variants exited 2 after 4079, 4082 and 4083 milliseconds, while the parent commit refused the same three records in 581, 571 and 555 milliseconds with the schema diagnostic that names the completion marker. The consolidation therefore replaced an immediate, self-explanatory refusal with a maximal-latency and misleading one at the default 1800-second deadline, and the occupied round then needs the documented removal recovery; Fix: keep the completion probe more permissive than the validator, comparing the marker against the last line after trimEnd, or trim trailing whitespace as well as newline runs before the last-nonempty-line comparison, so such records reach validateReviewRecord and fail fast, and add a regression asserting exit 2 with the schema diagnostic well inside a short deadline for a record whose final line is whitespace only.
- [Minor] lane.mjs:1926 - The new top-level review error boundary reports only that private evidence may have been retained, but the same catch also covers the window after the public record has been created, where REFERENCE requires the operator to inspect a retained public file and decide about committing or removing it. A mutation probe on a system-temp copy that threw immediately after the exclusive public write exited 2 with empty stdout, left the untracked public record in the lane worktree, and printed only the private-evidence sentence, so an operator can miss the artifact that later blocks check and promote on a dirty tree; Fix: extend the generic diagnostic to say that a public record may also have been created and must be inspected, reusing the late-publication wording, and cover it with a regression that injects a post-publication failure.
- [Minor] docs/REVIEW_TEMPLATE.md:81 - The round-four documentation states the consecutive-entry rule only for Findings, although Non-claims and Unverified enforce the same rule; probes with one blank line between two bullets refused with exit 2 in both sections, and a wrapped continuation line refused as well. Stating the rule for one list while the neighbouring sentence describes the other two as simply None or bullets reads as permission to separate those entries, which is the unstated-rule trap round three reported for Findings; Fix: extend the sentence in the template required-output section and in the REFERENCE schema paragraph so it says that Findings, Non-claims and Unverified entries each occupy consecutive lines with no blank line between them.
